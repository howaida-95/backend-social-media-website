# Implementing Posts and Uploads from Scratch

This guide explains how to build the posts and uploads backend in this project, in dependency order. It covers the purpose of each layer, how a post image moves through the system, and what to verify before calling the feature complete.

The examples assume the current stack: Express, TypeScript, Sequelize, MySQL, Zod, and Multer.

## 1. Start with the requirements and API

Write down the user-visible operations before creating models or routes. A minimal posts feature needs:

- Create a text-only post, image-only post, or text-and-image post.
- Read a feed and an individual post.
- Edit and delete only the signed-in user's post.
- Like and unlike a post, with at most one like per user.
- Add, list, edit, and delete comments, with ownership checks for edits/deletes.
- Upload an image and associate it with a post.

Agree on request and response shapes first. The current route layout is:

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/v1/feed?limit=20&cursor=...` | Read a page of posts |
| `POST` | `/api/v1/posts` | Create a post |
| `GET` | `/api/v1/posts/:id` | Get a post and its summary |
| `PATCH` | `/api/v1/posts/:id` | Edit the signed-in user's post |
| `DELETE` | `/api/v1/posts/:id` | Delete the signed-in user's post |
| `POST` | `/api/v1/posts/:id/like` | Like a post |
| `POST` | `/api/v1/posts/:id/unlike` | Unlike a post |
| `GET` | `/api/v1/posts/:id/likes` | List likes |
| `POST` | `/api/v1/posts/:id/comments` | Add a comment |
| `GET` | `/api/v1/posts/:id/comments` | List comments |
| `PATCH` | `/api/v1/posts/:id/comments/:commentId` | Edit the signed-in user's comment |
| `DELETE` | `/api/v1/posts/:id/comments/:commentId` | Delete the signed-in user's comment |
| `POST` | `/api/v1/uploads/image` | Upload one image (`multipart/form-data`, field `file`) |

The upload endpoint returns an `uploadId` and URL. The client uploads each image separately, then sends the resulting IDs as `uploadIds` when creating a post. Keeping upload and post creation separate makes file transport independent from ordinary JSON post data.

## 2. Design the data before writing endpoints

### Posts

A post belongs to one user and may refer to multiple uploaded images through the `post_images` join table. The `posts` table has:

- `id`: primary key.
- `user_id`: required foreign key to `users.id`.
- `content`: nullable text, so image-only posts are possible.
- timestamps and `deleted_at`.

Each row in `post_images` links a post to an upload and records its display position. Its unique index on `upload_id` ensures an uploaded file is attached to at most one post, while a post can have multiple images. Existing `posts.upload_id` associations are migrated to `post_images`.

Create posts with `{"content":"...","uploadIds":[12,13]}`. Create, feed, and detail responses include ordered `postImages` entries, each with its associated `upload` metadata.

### Uploads

An upload is file metadata, not the file bytes. The existing `uploads` table records:

- uploader (`user_id`);
- stable storage identifier (`public_id`);
- public URL (`url`);
- original name, MIME type, and size;
- purpose (`post`, `avatar`, `cover`, etc.);
- status (`pending` or `attached`);
- resource type and optional dimensions/format;
- timestamps and soft-delete time.

Keeping metadata in SQL lets the app check ownership and purpose, clean up abandoned uploads, and replace local disk/object storage later without changing the post's core data model. Store actual bytes in storage, not in a SQL text/blob field.

The migration is the source of truth for production schema. Define matching Sequelize attributes, field mappings, indexes, and constraints in the model. Use migrations rather than relying on `sequelize.sync()` so schema changes are repeatable and reviewable.

## 3. Create the models and associations

Create a Sequelize `Post` model and an `Upload` model that match their migrations. Use `underscored: true`, explicit `field` names when needed, timestamps, and paranoid deletes consistently with the other models in this backend.

Register relationships in the central model setup:

```ts
User.hasMany(Post, { foreignKey: 'userId', as: 'posts' });
Post.belongsTo(User, { foreignKey: 'userId', as: 'user' });

Upload.belongsTo(User, { foreignKey: 'userId', as: 'user' });
Post.hasMany(PostImage, { foreignKey: 'postId', as: 'postImages' });
PostImage.belongsTo(Upload, { foreignKey: 'uploadId', as: 'upload' });
Upload.hasMany(PostImage, { foreignKey: 'uploadId', as: 'postImages' });
```

Do the same for `Post`/`Comment` and `Post`/`Like`. These aliases are important: repository queries use names such as `association: 'user'`, so model setup and queries must agree exactly. Import the central association setup before serving requests.

For likes, enforce uniqueness in the database on `(user_id, post_id)`. Application-level checks alone are not enough: two concurrent requests can both pass a check and insert duplicates. The existing likes table already has this constraint.

## 4. Build the module in layers

Keep HTTP parsing, business rules, and database operations separate:

1. **Validation**: Zod schemas for post/comment bodies and pagination. Reject malformed inputs before controller logic. A post must contain text or an image reference; comment text should be non-empty and bounded.
2. **Routes**: Define paths and middleware order. Apply authentication to private operations, body validation to writes, and upload middleware only to upload routes.
3. **Controller**: Read validated input and `req.user.id`, call a service, and select HTTP status/response shape. Parse route IDs and cursors explicitly; never trust a client-supplied user ID.
4. **Service**: Apply feature rules such as “post exists,” “caller owns post,” “upload belongs to this caller and has purpose `post`,” and “upload has not already been attached.”
5. **Repository**: Encapsulate Sequelize queries. Keep ownership conditions in the query (`where: { id, userId }`) as well as the service authorization rule where appropriate.
6. **Model and migration**: Persist constraints so correctness survives concurrent requests and direct database access.

This structure helps you tell whether a bug belongs to HTTP input, business policy, or persistence instead of mixing every responsibility in one controller.

## 5. Implement upload handling

### 5.1 Configure Multer narrowly

Use `memoryStorage()` when the service explicitly writes the buffer to local storage, or use a storage adapter for a cloud provider. Apply:

- one expected multipart field (`file`);
- a strict maximum size;
- an allowlist of image MIME types;
- a generated storage key rather than the client filename.

MIME type comes from the request and can be forged. For production, inspect file signatures (magic bytes) and optionally decode the image before trusting it. Do not accept arbitrary paths or filenames from the client.

### 5.2 Write to storage and record metadata

The upload service should:

1. Require an authenticated uploader.
2. Reject a missing, oversized, or disallowed file.
3. Generate a random storage identifier and safe extension.
4. Save the bytes to local disk in development or object storage in production.
5. Insert an `uploads` row with uploader, storage key, URL, MIME type, size, purpose, and status.
6. Return only the fields the client needs, such as `uploadId` and `url`.

The controller should not contain file-system or cloud SDK logic. This makes the storage implementation replaceable and easier to test.

### 5.3 Handle failures in both systems

The filesystem/object store and SQL database do not share a transaction. If writing the metadata row fails after the file is stored, delete the newly written file and rethrow the original error. If deletion fails too, log both failures so an operator can clean the orphan.

Prefer the state transition:

```text
upload bytes → create metadata with pending status
             → create post and attach upload in a DB transaction
             → mark upload attached
```

This lets a cleanup job find old pending uploads. If post creation fails, the upload remains pending and can be retried or removed. The current upload service stores a row with `status: 'attached'` before it is linked to a post; adjust this when implementing ownership/attachment checks.

### 5.4 Serve local files or use object storage

For local development, mount the upload directory as static content. Build the public URL from a configured public base URL, not a hard-coded `http://localhost`, because clients may access the API through another hostname, TLS proxy, or deployment domain.

Local disk is generally not durable or shared across production instances. For production, use object storage (for example S3-compatible storage) and persist the object key plus a canonical URL. Keep storage behind a small interface so the upload service does not depend directly on one provider.

## 6. Attach an upload safely while creating a post

The client should not be allowed to attach somebody else's upload by guessing an ID. Before inserting the post, verify all of these:

- the upload exists and is not deleted;
- `upload.userId` equals the signed-in user's ID;
- `upload.purpose` is `post`;
- upload status allows attachment;
- it is not already assigned if uploads are single-use.

Then, in a database transaction, create the post with `userId` taken from authentication and create one ordered `post_images` row for each verified upload. The unique `post_images.upload_id` constraint prevents one upload from being attached more than once. If the transaction fails, neither SQL change should persist.

Post media is represented by verified upload IDs and returned through the ordered `postImages` association. Clients cannot provide arbitrary media URLs.

## 7. Implement post and feed operations

### Create, read, update, delete

- **Create**: validate text/media; take `userId` from authentication; validate and attach the upload; return `201 Created`.
- **Read detail**: fetch post, author, like count, comment count, and whether the current user liked it. Return `404` if it does not exist.
- **Update**: include both post ID and authenticated user ID in the update lookup. Return `403` for another user's post and `404` for a missing post. Validate every editable field.
- **Delete**: verify ownership, then delete or soft-delete related data consistently. Use a SQL transaction for database changes. If deleting stored files, do it after the database operation or record a cleanup task; storage deletion cannot be rolled back by a SQL transaction.

### Feed pagination

Use stable keyset pagination rather than a growing SQL offset. Sort by `created_at DESC, id DESC`; the `id` is a tie-breaker for posts with identical timestamps. A cursor contains the last row's timestamp and ID. The next query is conceptually:

```sql
WHERE created_at < :cursorCreatedAt
   OR (created_at = :cursorCreatedAt AND id < :cursorId)
ORDER BY created_at DESC, id DESC
LIMIT :limitPlusOne
```

Fetch one extra row to calculate `hasMore`, return only the requested page, and encode the last returned row as `nextCursor`. Validate and bound the limit and reject malformed cursor values. A cursor is a pagination marker, not an authorization token.

Include the author in the feed query. Fetch grouped like/comment counts and current-user likes for the page's post IDs in batches; avoid querying counts separately for every post (the N+1 query problem). Index columns used by filters and sort order as traffic grows.

## 8. Implement likes and comments

### Likes

Use the `Like` model and unique `(user_id, post_id)` constraint. An idempotent like can use `findOrCreate`; unlike deletes only the row belonging to the current user and post. Check that the post exists before inserting. Return a predictable result and test duplicate like requests.

### Comments

Create comments with both `postId` and authenticated `userId`. Validate and trim content; the current model limits comments to 1,000 characters. List comments in a stable order and include safe author fields. Scope update/delete queries by `commentId`, `postId`, and `userId` so a user cannot alter another user's comment or act on a comment under another post.

## 9. Verify integration and errors

Register post/upload routes in the Express app after common middleware and before the not-found handler. Ensure associations load before requests run. Keep the error middleware last. For Multer errors, map file-size and invalid-file failures to clear `400` responses rather than an opaque `500`.

Manually or automatically verify:

- unauthenticated requests return `401`;
- invalid IDs, body fields, cursors, and file types/sizes are rejected;
- a text-only post and an image-only post can be created;
- an uploaded image can be retrieved using the returned URL;
- another user cannot attach an upload or edit/delete a post/comment they do not own;
- liking the same post twice does not create duplicate rows;
- the feed ordering is stable across pages with equal timestamps and does not repeat rows;
- deleting a post removes or soft-deletes associated comments/likes as intended;
- a database failure after writing a file does not silently leave an untracked file.

Run migrations against a clean development database and run the TypeScript check and tests after wiring each layer.

## 10. Current implementation notes

Use these notes to distinguish the existing code from the safer end state described above:

- The modules are in `src/modules/posts` and `src/modules/uploads`; route mounting and local static serving are in `src/app.ts`.
- The upload route accepts one multipart field named `file`, allows JPEG/PNG/WebP/GIF, and limits the file to 5 MiB.
- The current upload service saves locally and inserts upload metadata, but hard-codes `http://localhost` in the returned URL.
- If the database insert fails after the local file write, the current upload service does not remove that file. Add the compensation/cleanup behavior described above.
- The current upload flow marks metadata `attached` immediately and does not yet verify that a post uses an upload owned by the caller. Add the pending-to-attached checks before relying on `uploadId`.
- The post request accepts `uploadIds`; validate the uploads and return their URLs through the post-image association.
- The post schema currently allows `content` to be omitted or empty even when no image is supplied. Add a cross-field refinement requiring text or an image. The update controller currently edits only `content`; either keep update text-only or explicitly implement and authorize media replacement.
- The post table's unique `upload_id` constraint supports only one post per upload. Use a separate join table for multiple post images.
- `share` and `repost` are not in scope for the current schema. Add explicit tables, constraints, endpoints, and behavior before implementing them; do not add controller calls to nonexistent model methods.
